## 订单跨日与统计归属

### 业务前提

Legero 的订单工作台以“当天营业”为主要使用场景：

- 订单页面主要处理当天创建的订单。
- 门店正常营业不会持续到凌晨。
- 正常业务中，订单通常会在创建当天完成。
- 因此 `created_at` 与 `completed_at` 基本会落在同一个业务日期。

订单跨业务日完成不属于正常业务流程，不需要为了这一极端情况改变现有订单清理、工作台展示等产品语义。

### 统计日期以完成时间为准

日报、周报、月报以及 `/api/stats/daily` 的统计归属统一以 `completed_at` 为准，而不是 `created_at`。

仅统计：

```text
completed_at IS NOT NULL
```

业务日期按照配置的业务时区 `biz.timezone` 判断。

例如，对于业务日期 `D`：

```text
D 00:00 <= completed_at < D+1 00:00
```

因此：

- 未完成订单不进入营业统计。
- 订单完成后，计入 `completed_at` 所属业务日期。
- 如果订单被切回未完成状态，`completed_at` 被清空，则立即从统计中移除。
- 如果之后再次完成，则按照新的 `completed_at` 重新归属。

### 高峰时段按下单时间统计

报表的日期归属、营收、完成单量等指标仍然以 `completed_at` 为准；高峰时段是其中的例外，仅描述该业务日内有效订单的下单需求。

对于业务日期 `D`，订单只有同时满足以下条件，才进入 `D` 的高峰时段统计：

- `created_at` 非零；
- `created_at <= completed_at`；
- `D 00:00 <= created_at < D+1 00:00`；
- `D 00:00 <= completed_at < D+1 00:00`。

符合条件的订单按 `created_at` 的本地墙上时刻划分为半小时桶，返回订单数最高的前 5 个非空时段；订单数相同时，较早的时段优先。

因此，前一业务日下单、`D` 完成的合法跨日订单仍计入 `D` 的营收、完成单量和平均出餐时长，但不计入 `D` 的高峰时段。`created_at > completed_at` 的异常订单不计入高峰时段，也不计入平均出餐时长。

### 跨日订单

虽然正常营业流程基本不会产生跨日订单，但系统仍保持明确且一致的防御性语义。

例如：

```text
created_at   = 2026-08-18 23:55
completed_at = 2026-08-19 00:05
```

该订单在统计上归属于 `2026-08-19`，而不是 `2026-08-18`。

原因是经营统计描述的是订单实际完成的时间，因此统一使用 `completed_at` 判断统计归属。

这一规则主要用于保证异常数据和边界情况下统计结果仍然确定，并不代表系统将跨日经营作为正常业务场景支持。

### 与 `clear before_today` 的关系

`clear before_today` 属于订单工作台的数据清理行为，与 reporting 的日期归属规则是两个不同概念。

当前语义保持不变：

- `clear before_today` 按订单的创建日期清理今天以前创建的历史订单。
- reporting 按订单的 `completed_at` 判断统计归属。

正常营业流程中，订单会在创建当天完成，因此通常有：

```text
created_at business date ≈ completed_at business date
```

所以正常情况下，`clear before_today` 不会影响当天日报。

对于理论上的异常跨日订单，不为了该极端情况修改 `clear before_today` 的产品语义。

两套规则服务于不同目的：

- 工作台清理规则按照订单生命周期和创建日期理解。
- reporting 按照实际完成时间 `completed_at` 归属。
- 不要求两套规则在异常跨日数据下完全等价。

### 实现建议

统计查询应优先将业务日期转换为明确的时间窗口，再使用 `completed_at` 做范围查询：

```sql
WHERE workspace_id = ?
  AND completed_at >= ?
  AND completed_at < ?
```

其中两个时间参数分别表示业务时区下的 `start_at` 和 `end_at`。

相比对 `completed_at` 做日期函数转换，这种方式：

- 明确表达 `[start, end)` 的周期边界；
- 可以复用日报、周报、月报的统一周期解析逻辑；
- 可以更好地利用 `(workspace_id, completed_at)` 索引；
- 避免数据库或服务器默认时区影响统计结果。

### 测试要求

跨日完成作为防御性边界测试保留。

例如：

```text
created_at   = D 23:55
completed_at = D+1 00:05
```

预期：

```text
D   -> 不包含该订单
D+1 -> 包含该订单
```

但跨日场景不作为修改订单工作台、订单清理或正常营业流程的产品设计依据。
